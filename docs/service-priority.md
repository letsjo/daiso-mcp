# 차기 서비스 우선순위

작성일: 2026-03-07 (KST)

## 결정 결과

1. `Emart24`
2. `GS25`
3. `CU`

## 판단 기준

- 앱 트래픽 실측 없이 웹 채널만으로 제공 가능한 기능 수
- 현재 `src/services/*` 구조에 자연스럽게 들어오는 구현 난이도
- 인증, 세션, 403, 우회 의존성 같은 운영 리스크
- "가까운 매장 찾기 + 상품 탐색"까지 한 번에 제공할 수 있는 사용자 가치

## 서비스별 판정

### 1. Emart24

- 현재 바로 가능한 범위:
  - `emart24_find_nearby_stores`
  - `emart24_search_products`
- 우선순위 1위로 둔 이유:
  - `/api1/store`가 JSON으로 매장 좌표, 주소, 서비스 플래그를 제공해 기존 매장 도구 패턴과 가장 잘 맞습니다.
  - `/api1/goods`가 공개 웹 상품 카탈로그를 제공해 재고 없이도 두 번째 도구를 빠르게 만들 수 있습니다.
  - 재고는 앱 실측 전까지 보류해도 서비스 가치가 충분합니다.
- 근거 문서:
  - `docs/emart24-network-analysis-result.md`

### 2. GS25

- 현재 바로 가능한 범위:
  - `gs25_find_nearby_stores`
- 2위로 둔 이유:
  - 매장 조회 API가 JSON 기반이라 구현은 쉽습니다.
  - 상품 API 흔적은 있지만 `CSRFToken`, 세션, 403 제약이 있어 서버 측 재현성이 아직 불안정합니다.
  - 재고는 우리동네GS 앱 실측 전까지 구현 근거가 부족합니다.
- 근거 문서:
  - `docs/gs25-network-analysis-result.md`

### 3. CU

- 현재 바로 가능한 범위:
  - `cu_find_nearby_stores`
- 3위로 둔 이유:
  - 매장 조회는 가능하지만 HTML 파싱 중심이라 구현 이점이 GS25, Emart24보다 작습니다.
  - 웹 채널에서 상품/재고 확장 여지가 가장 적게 확인됐습니다.
  - 현재 레포 관점에서는 "빠르게 출시 가능한 도구 수"가 가장 적습니다.
- 근거 문서:
  - `docs/cu-network-analysis-result.md`

## 권장 구현 순서

1. `Emart24`를 먼저 추가하고 `find_nearby_stores`, `search_products` 두 도구를 함께 출시합니다.
2. 다음으로 `GS25`의 `find_nearby_stores`를 추가해 편의점 카테고리 커버리지를 넓힙니다.
3. `CU`는 매장 조회 단일 도구 범위로 후순위에 둡니다.
4. 세 서비스 공통으로 앱 트래픽 실측이 끝나면 재고 도구 우선순위를 다시 평가합니다.

## 구현 메모

- 1차 목표는 "재고"보다 "주변 매장 + 상품 탐색" 조합을 빨리 늘리는 것입니다.
- 따라서 다음 실제 구현 작업은 `Emart24` 서비스 스캐폴드와 매장/상품 API 정규화부터 시작하는 것이 가장 효율적입니다.
