## 결론 요약

- 지금 단계에서는 `자동 생성 스크립트`를 바로 추가하지 않는 편이 낫습니다.
- 대신 현재 문서 템플릿을 유지하고, 다음 실제 구현 서비스(`Emart24`)가 들어온 뒤 공통 패턴을 한 번 더 확인한 다음 scaffold를 도입하는 것이 안전합니다.
- 즉, 현재 판정은 `지금은 보류`, `후속 서비스 1개 추가 후 재평가`입니다.

## 왜 바로 만들지 않는가

현재 서비스별 편차가 아직 큽니다.

| 서비스     | 특징                                           |
| :--------- | :--------------------------------------------- |
| Daiso      | 상품, 매장, 가격, 재고까지 가장 넓은 소매 패턴 |
| Oliveyoung | Zyte 의존, 매장/재고 조합형                    |
| Megabox    | 영화관/영화/잔여좌석 중심                      |
| CGV        | 서명 헤더, 403 fallback, 시간표 특화           |

이 상태에서 generator를 고정하면 공통 분모보다 예외 처리가 더 많아질 가능성이 큽니다.

## 지금 문서 템플릿이 충분한 범위

현재 [docs/new-service-template.md](/Users/hyunohjo/conductor/workspaces/daiso-mcp/casablanca/docs/new-service-template.md)는 아래 항목을 이미 커버합니다.

- 서비스 디렉터리 구조
- `index.ts` 기본 형태
- 테스트 추가 위치
- 문서와 OpenAPI 반영 체크리스트

즉, 지금 부족한 것은 "파일 이름을 자동으로 만들어주는 도구"보다 "공통 패턴이 충분히 안정화됐는지"입니다.

## generator를 지금 넣을 때의 문제

1. 소매 서비스와 영화 서비스의 기본 도구 세트가 다릅니다.
2. 일부 서비스는 `zyteApiKey` 같은 옵션 생성자가 필요하고, 일부는 필요 없습니다.
3. REST 라우트/핸들러 추가 여부도 서비스마다 다릅니다.
4. OpenAPI 모듈 반영 위치도 서비스 종류에 따라 달라집니다.

결과적으로 지금 generator를 넣으면 생성 직후 다시 손으로 고치는 비율이 높을 가능성이 큽니다.

## 나중에 도입한다면 권장 형태

### 권장 시점

- `Emart24`까지 구현한 뒤
- 편의점 계열 서비스 2개 이상이 생겼을 때

### 권장 최소 범위

- `src/services/{service}/`
  - `api.ts`
  - `client.ts`
  - `index.ts`
  - `types.ts`
  - `tools/`
- `tests/services/{service}/`
  - `client.test.ts`
  - `index.test.ts`
- `docs/{service}-network-analysis-result.md` 빈 문서

### generator가 해도 되는 일

- 파일/디렉터리 생성
- 서비스 ID, 표시 이름 치환
- 기본 export, 기본 테스트 골격 생성

### generator가 하지 말아야 할 일

- OpenAPI 경로 자동 삽입
- 서비스별 실제 도구 목록 추론
- 외부 API 엔드포인트나 스키마 생성

이 부분은 여전히 사람 검토가 필요합니다.

## 권장 후속 절차

1. 다음 실제 서비스 구현은 현재 문서 템플릿으로 진행
2. 구현 과정에서 반복 수정된 파일 목록을 기록
3. 두 번째 편의점 서비스까지 끝나면 그 공통 패턴을 기준으로 `scripts/scaffold-service.mjs` 여부를 다시 판단
