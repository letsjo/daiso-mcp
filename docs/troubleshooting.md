# 외부 연동 트러블슈팅

작성일: 2026-03-07 (KST)

이 문서는 Zyte, 외부 차단, 403, 타임아웃처럼 운영 중 자주 맞닥뜨릴 수 있는 문제와 대응 절차를 정리합니다.

## 빠른 분류표

| 증상                                 | 주로 영향받는 서비스          | 우선 확인할 것                                         |
| :----------------------------------- | :---------------------------- | :----------------------------------------------------- |
| `ZYTE_API_KEY가 설정되지 않았습니다` | Oliveyoung, 일부 CGV fallback | 로컬 `.env`, Cloudflare Worker Secret                  |
| `Zyte API 호출 실패: 401/403`        | Oliveyoung, 일부 우회 호출    | API 키 유효성, 사용량, 계정 상태                       |
| `CGV API 호출 실패: 403`             | CGV                           | Zyte fallback 사용 여부, 직접 호출 차단 여부           |
| `... 요청 시간 초과`                 | 전 서비스                     | 외부 서비스 지연, 범위 과다, timeout 설정              |
| 응답 구조는 200인데 파싱 실패        | 전 서비스                     | 외부 사이트 응답 구조 변경, fixture/계약 테스트 재검토 |

## 1. Zyte 관련 문제

### 증상

- `ZYTE_API_KEY가 설정되지 않았습니다. .env 또는 Cloudflare Worker Secret을 확인해주세요.`
- `Zyte API 호출 실패: 401`
- `Zyte API 호출 실패: 403`
- `올리브영 API 응답 실패: unknown`

### 확인 순서

1. 로컬 개발이면 `.env`에 `ZYTE_API_KEY`가 있는지 확인합니다.
2. 배포 환경이면 Cloudflare Worker Secret에 `ZYTE_API_KEY`가 설정돼 있는지 확인합니다.
3. 키 자체가 만료됐거나 권한이 바뀌지 않았는지 Zyte 대시보드에서 확인합니다.
4. 같은 요청이 계속 실패하면 외부 사이트 차단 정책이 바뀌었는지 의심합니다.

### 대응 메모

- Oliveyoung는 현재 Zyte 의존도가 높아 키가 없으면 관련 기능이 바로 실패합니다.
- CGV는 직접 호출이 막히는 경우에만 Zyte fallback을 사용합니다.
- 배포 후 점검은 먼저 기본 스모크 테스트를 돌리고, 필요할 때만 선택 점검을 추가합니다.

## 2. 외부 차단과 403 대응

### CGV

- 직접 호출이 `403`이면 현재 구현은 Zyte API 키가 있을 때 fallback을 시도합니다.
- `ZYTE_API_KEY`가 없으면 `CGV API 호출 실패: 403`으로 끝납니다.

### GS25, Emart24, CU 후보군

- 현재 후보 서비스 리서치 문서에서도 세션, CSRF, 앱 전용 흐름이 관찰됩니다.
- 새 서비스를 추가할 때 `curl` 재현만 믿지 말고 브라우저 또는 앱 실측 근거를 먼저 확보해야 합니다.

### 대응 절차

1. 같은 요청을 짧은 시간에 반복하지 말고 간격을 둡니다.
2. 브라우저 기반 실측 문서와 현재 응답을 비교합니다.
3. 우회 수단이 이미 있는 서비스는 fallback 경로가 정상 동작하는지 확인합니다.
4. 우회가 없는 서비스는 일단 기능을 보수적으로 축소하는 편이 안전합니다.

## 3. 타임아웃 대응

### 대표 에러 메시지

- `메가박스 상영 목록 조회 시간 초과`
- `메가박스 지점 정보 조회 시간 초과`
- `CGV API 요청 시간 초과`
- `올리브영 API 요청 시간 초과`

### 확인 순서

1. 외부 서비스 자체 응답이 느린지 브라우저에서 먼저 확인합니다.
2. 조회 범위를 줄일 수 있는지 봅니다.
3. 가능한 경우 `limit`, `pageSize`, `timeoutMs`를 보수적으로 조정합니다.
4. 일시 장애인지 확인하기 위해 짧게 재시도합니다.

### 실무 팁

- 영화 서비스는 날짜, 극장, 영화 코드를 함께 좁히면 타임아웃 확률이 줄어듭니다.
- 소매 서비스는 기본 좌표와 넓은 검색어를 함께 쓰면 응답량이 커질 수 있습니다.

## 4. 응답 구조 변경 대응

### 징후

- HTTP는 `200`인데 테스트가 필드 파싱 실패로 깨집니다.
- 스모크 테스트에서 성공은 하지만 핵심 필드가 비어 있습니다.
- 계약 테스트 fixture와 실제 응답이 눈에 띄게 달라집니다.

### 대응 절차

1. `tests/fixtures/`의 대표 응답과 실제 응답을 비교합니다.
2. `docs/*-network-analysis-result.md`의 기존 근거와 달라진 지점을 기록합니다.
3. 파서 수정 후 계약 테스트와 스모크 테스트를 함께 갱신합니다.
4. OpenAPI나 prompt 설명이 바뀌면 관련 문서도 같이 수정합니다.
